# Workspace Audit Findings

Read-only diagnostic sweep of all packages under `src/` plus `docs/`, performed 2026-07-08.
No code was modified. Every finding was verified against the current source; line numbers
refer to the working tree at commit `3965599`.

## Summary

The codebase is functionally rich and mostly well-commented, and the recent hardening work
(JSON extraction, retry-on-blank, request timeouts) is solid. The two weakest areas are:
**(1) failure reporting on the real-robot path** — the executor reports trajectory and
gripper failures as success, and the plan manager can resume a cancelled plan — which means
dry-run-green does not imply hardware-safe; and **(2) copy-paste divergence** — the three
planner nodes, the two executors, the three GUI supervisors, and the two LLM/VLM client
stacks each contain near-identical blocks that have already started drifting (the
`offset` default and `_save_frame` return-type divergences are drift that has already
happened). Configuration health is good: every `Settings` field in `config.py` is read
somewhere, and all node `declare_parameter` calls default from `settings`; the drift risk
is in launch-file literals and docstrings, not the nodes.

## Bugs

### Critical — robot safety / hard crashes

- **[robo_reason_executor/ur5_skill_executor_node.py:342]** Trajectory failure is reported
  as skill success. `_send_trajectory_and_wait` returns `result_holder[0] is not None`,
  but a `FollowJointTrajectory` result is delivered even when the controller **aborts**
  (tolerance violation, scaling stop). A failed approach/pick returns `True`, the plan
  continues, and the gripper closes on air (or worse). Fix direction: check
  `status == GoalStatus.STATUS_SUCCEEDED and result.error_code == SUCCESSFUL`.

- **[robo_reason_executor/ur5_skill_executor_node.py:441-454]** Gripper commands can never
  fail. `_gripper_set_pin` ignores the `done.wait(timeout=5.0)` return value, the `SetIO`
  response's `success` field, and exceptions in `future.result()`, then returns `True`
  unconditionally — so `raise RuntimeError('gripper close failed')` at `:572` is
  unreachable. A dead driver or rejected IO write "succeeds" and the pick lifts nothing.
  Fix: `return done.wait(...) and future.result().success`.

- **[vlm_camera_service/camera_services_node.py:360-367]** Uncalibrated deprojection
  returns `success=True` with **camera-frame** points, and neither consumer checks
  `frame_id` (`robo_reason_planner/vlm_planner_node.py:406-407`,
  `vlm_llm_planner_node.py:385-386`) — if a plan runs before the ChArUco lock, the arm is
  commanded in camera-optical coordinates with only a warning in the camera log. Fix:
  return `success=False` ("not calibrated"), or have planners assert
  `frame_id == 'base_link'`.

- **[vlm_camera_service/mock_camera_service_node.py:51-61]** The mock camera node cannot
  start at all: `images_dir = os.path.join(os.getcwd(), images_dir)` converts the `Path`
  to `str`, then `images_dir.exists()` raises `AttributeError` unconditionally. Fix:
  `images_dir = Path.cwd() / Path(...)` (join is a no-op for the absolute default anyway).

- **[robo_reason_manager/plan_manager_node.py:246]** Cancel/resume race: the emergency-stop
  handler clears `_stop_requested` at the end of the cancel, but the plan loop only checks
  the flag *between* steps (`:117`). If cancel fires during an un-cancellable skill (e.g.
  `wait`, which is a bare `time.sleep` in the executor — see below), the robot is sent
  home, the flag is cleared, the blocked skill then completes, and **the rest of the
  cancelled plan resumes from the home position**. The clear at `:79` (start of every new
  plan) already covers fresh plans; delete the end-of-cancel clear.

- **[robo_reason_manager/plan_manager_node.py:166,196-200]** Skill timeout (60 s) abandons
  a goal that is still moving the robot: on timeout the manager reports failure and
  returns without cancelling the goal, and `_active_goal_handle` stays stale. A `wait`
  step with `time > 60` (the validator allows any `time >= 0`,
  `plan_validator.py:75-78`) is a guaranteed false failure with the robot unattended.
  Fix: cancel the goal handle on timeout, clear `_active_goal_handle`, and derive the
  `wait` timeout from its `time` arg.

- **[robo_reason_executor/ur5_skill_executor_node.py:553,606,532-534]** Cross-goal mutable
  state: `pick` mutates `self._robot_model.tool` and only `release` restores it — a
  cancelled/aborted pick leaves a width-specific tool offset (up to ~32 mm Z error) in
  every subsequent motion. The ActionServer also uses a `ReentrantCallbackGroup` with an
  accept-all goal policy, so the manager's e-stop `move_home` (sent 0.3 s after cancel,
  `plan_manager_node.py:225-233`) can execute concurrently with the unwinding cancelled
  skill, sharing the non-thread-safe `_robot_model` and `_last_approach_*`. Fix: restore
  the tool in a `finally`; pass the offset per-call; add a goal callback that rejects a
  second concurrent goal.

- **[robo_reason_executor/ur5_skill_executor_node.py:654,453]** `wait` (`time.sleep(duration)`)
  and the 2 s gripper settle are un-cancellable — cancel polling exists only inside
  `_send_trajectory_and_wait`. This is the enabling half of the cancel/resume race above.
  The fake executor already sleeps in 0.1 s slices checking `is_cancel_requested`
  (`fake_skill_executor_node.py:57-74`) — copy that.

- **[vlm_camera_service/camera_services_node.py:606-609]** `_publish_charuco_axis` can
  crash the whole camera node: `cv2.projectPoints` returns negative pixel coords when the
  board is near the image edge, and assigning a negative int to `PixelArray`'s `uint32[]`
  raises inside the 2 Hz timer callback, which propagates out of `spin()`. Fix: clamp to
  `>= 0` or skip publishing when out of range.

- **[robo_reason_manager/plan_manager_node.py:74-79]** No mutual exclusion on
  `/execute_plan`: a second concurrent call is accepted (ReentrantCallbackGroup), clears
  `_stop_requested` (killing an in-progress cancel), and both loops clobber
  `_active_goal_handle`. Fix: a non-blocking busy flag that rejects the second plan.

### Correctness — non-fatal but wrong behavior

- **[robo_reason_executor/ur5_skill_executor_node.py:542-572]** `come_back` and
  `grasp_axis` are accepted end-to-end (schemas, prompts —
  `robo_reason_reasoning/skills.py:26` promises "return to the pre-grasp approach
  position after picking") but silently ignored by the real executor: `pick` never
  retracts, so the next `approach` starts a joint-space move **at table height with the
  object in hand**, sweeping it across the table. Fix: retract to the pre-grasp hover
  after `_gripper_close` (mirroring release), or delete the args everywhere so the
  contract is honest.

- **[robo_reason_reasoning/tot.py:113,126,191]** ToT crashes with `IndexError` when the
  very first `_generate_action_thought` returns an empty `sampled_actions` list: iteration
  1 sets `best_ids = []` (`:126`), the empty `db` produces no candidates, the loop breaks
  with `best_terminal is None`, and `:191` evaluates `best_ids[0]` on the empty list.
  Fix: raise a clear "model returned no candidate actions" error when `db` stays empty.

- **[robo_reason_reasoning/fhp_ffhp.py:75]** FHP/FFHP hard-fails on a bare-array plan
  response: `self._parse_json_response(raw, context='plan_task')['plan']` raises
  `TypeError`/`KeyError` if the model returns `[...]` instead of `{"plan": [...]}` —
  the exact shape `cot_sc.py:60-62` deliberately tolerates ("LLMs sometimes return the
  plan as a bare array"). Fix: apply the same both-shapes acceptance.

- **[robo_reason_reasoning/skills.py:105-116 + EmbodiedAgentsPrompts/*_prompts.py bbox
  variants]** In bbox grounding mode the prompt contradicts itself: the BBOX prompt bodies
  demand `[x_min, y_min, x_max, y_max]` (e.g. `fhp_ffhp_prompts.py:135-139`) but the
  `{action_placeholder1}`/`{skills}` placeholders they embed are filled from
  `UR5Skills.vlm_action_example_placeholder` / `vlm_skills`, which only exist in `[x, y]`
  point form (`skills.py:52-116`; `embodied_agent.py:54-56` selects by `use_vlm` only,
  never by `grounding_mode`). The model receives both "output a 4-element box" and an
  example showing a 2-element point. Fix: add bbox variants of the two placeholder strings
  and select them by `grounding_mode`.

- **[robo_reason_executor/fake_skill_executor_node.py:42-84]** The fake executor validates
  nothing: any skill name is accepted (real raises "Unknown skill"), required args are
  never checked (`pick` without `target_position` → fake OK, real KeyError→abort). A plan
  that dry-runs green can fail on step 1 against hardware. Fix: share one small
  skill-name/required-args validation function between both executors.

- **[robo_reason_executor/ur5_skill_executor_node.py:485 + fake_skill_executor_node.py:44]**
  `json.loads(goal_handle.request.skill_args_json)` sits outside the `try` block: a
  malformed payload escapes the execute callback, the goal never reaches a terminal state,
  and the manager blocks the full 60 s before failing with a misleading "timed out".

- **[robo_reason_manager/plan_manager_node.py:219,226]** The cancel path discards the
  `cancel_goal_async()` future and sleeps a fixed 0.3 s before sending `move_home` — if
  the executor rejects/delays the cancel, home is commanded while the previous motion is
  still active. Related: the home goal registers itself as `_active_goal_handle`, and the
  old goal's late result callback then nulls it (`:177-178`), so a second cancel cannot
  reach the in-flight home motion. Fix: wait on the cancel future / the original result
  before sending home.

- **[robo_reason_manager/plan_manager_node.py:183]** An exception inside
  `on_goal_response` (`future.result()` raising when the server died between
  `wait_for_server` and send) is swallowed by rclpy's callback machinery; `done_event`
  is never set and the caller stalls 60 s, then reports a bogus timeout. Fix: try/except
  in the callback that fills `result_holder` and sets the event.

- **[robo_reason_executor/ur5_skill_executor_node.py:383-390,399]** `_move_linear`
  silently drops waypoints whose IK fails (warn-and-skip). If many consecutive waypoints
  fail, the "linear" descent becomes one large joint-space jump executed over the same
  total duration — precisely on the pick/release moves where straight-line motion is the
  safety property. Fix: fail the move when more than a small fraction of waypoints is lost.

- **[robo_reason_gui/static/app.js:558-559 vs 497-550]** After any driver action, the
  **Reconnect** buttons stay disabled forever: `driverAction` disables
  `driverStart/driverReconnect/driverStop/headerReconnect`, but `renderDriver` (called by
  the poll) only re-enables `driverStart`/`driverStop` (`:519-520`) — it never touches
  `driverReconnect`/`headerReconnect`. Fix: set their `disabled` state in `renderDriver`
  alongside the other two.

- **[robo_reason_gui/static/app.js:806-809]** `applyLogLine` marks a step `done` on any
  `"[Step N]"` log line regardless of content — a step that logs a failure line is
  rendered green, and the later error path (`:884`) then can't find it among `.pending`
  steps. Fix: only mark done on the success pattern (or parse the outcome token).

- **[robo_reason_gui/robo_reason_gui/app.py:167-178]** Idle-WebSocket queue leak: the
  handler blocks on `await queue.get()`; a client that disconnects while no logs flow
  never triggers `WebSocketDisconnect` (only `send_json` raises it), so the queue stays
  registered in `bridge._log_subscribers` indefinitely (page reloads mid-session
  accumulate them). Fix: race `queue.get()` against `ws.receive()` so disconnects are
  observed.

- **[robo_reason_gui/robo_reason_gui/stack_supervisor.py:28-37,241-253 +
  ur_driver_supervisor.py:34-41,126-149]** `_reap_stale` SIGKILLs every process whose
  full command line matches `pgrep -f <pattern>` — patterns like `ur5_skill_executor_node`

  and only the GUI's own pid/ppid are excluded. Fix: anchor patterns to the executable
  (`pgrep -f 'python3 .*/ur5_skill_executor_node$'`-style) or check `/proc/<pid>/comm`.

- **[robo_reason_gui/robo_reason_gui/ur_driver_supervisor.py:295,299-313]** Stale
  `_error_event` race: the event is cleared in `_spawn` before the new pump thread starts,
  but the *previous* attempt's pump thread may still be draining its buffer and can set
  the event afterwards, aborting the fresh attempt spuriously (costs one retry cycle).
  Fix: use a per-attempt event object passed to the pump thread.

- **[robo_reason_gui/robo_reason_gui/stack_supervisor.py:176]** `stop()` calls
  `os.getpgid(proc.pid)` without catching `ProcessLookupError`; if the launch process
  exits between the `is_running()` check and this call, the exception propagates to the
  FastAPI route as a 500. (The driver supervisor's `_terminate` at
  `ur_driver_supervisor.py:380-382` handles exactly this.) Fix: same try/except.

- **[robo_reason_planner/robo_reason_planner/command_grounding.py:20-31]** Object-name

## Simplification opportunities

Ordered by (verbosity removed × drift-risk removed) vs. change risk.

1. **~120 duplicated lines in `llm_client.py`** — `_call_openai` (`:101-159`) and
   `_call_nebius` (`:161-219`) are byte-identical (the base-url difference lives in
   `_initialize_client`). `vlm_client.py:237-238` already does it right
   (`_call_nebius = delegate to _call_openai`). Delete one body.

## Needs a decision

Ambiguities where the code may be compensating for hardware reality — flagged as
questions rather than prescriptions.

1. **Release lift semantics (executor ↔ planner contract)** —
   `ur5_skill_executor_node.py:581-587` does `release_pos[2] += object_height`, assuming
   a top-grasp; the VLM pipelines grasp mid-body (`PICK_GRASP_DEPTH_FRACTION=0.5`) and
   compensate by passing `object_height = height - descent`
   (`vlm_planner_node.py:443-453`) — consistent. But the **LLM** pipeline's
   `object_height` comes straight from the model/scene with a top-surface pick target: is
   the LLM-mode release intentionally uncompensated (objects released ~half a height too
   high whenever the pick contact wasn't the top)?

2. **bbox `grasp_width` vs. the local-plane-centroid filter** —
   `vlm_planner_node.py:388-391` deprojects the bbox's left/right edge midpoints to
   measure real grasp width, but with `LOCAL_PLANE_CENTROID_ENABLED=True` (default,
   `config.py:133`) the Deproject service re-targets each pixel toward the local
   top-plane centroid — doesn't that systematically distort the measured width? Should
   width-measurement pixels bypass the centroid refinement?

3. **Validator skips holding-state checks only for `mode == 'VLM'`**
   (`plan_validator.py:14,59,69`) — a VLM plan with `pick, pick` or a leading `release`
   executes unchecked while `VLM_LLM` keeps the guardrails. Intentional (VLM plans lack
   object identity) or an oversight?

4. **Cancel always commands `move_home`, even when idle**
   (`plan_manager_node.py:229-233`) — pressing e-stop with nothing running moves the
   robot. Deliberate "safe posture", or should it no-op when nothing is executing?

5. **Startup gripper pulse** (`ur5_skill_executor_node.py:180-183`) — the HIGH→LOW pulse
   to defeat pendant edge detection performs a full close (2 s) then open at every node
   start; if the robot boots with fingers around an object left from a crashed session it
   will squeeze it. Accepted trade-off?

6. **Tool offset restored to mid-open (0.207) right after the gripper is driven fully
   open** (`:606`; fully-open calibration ≈ 0.175 per `config.py:94-98`). Deliberate
   "known baseline until next pick"?

7. **`_horizontal_approach` hover z equals object z exactly** (`:264`) — the joint-space
   move to hover can drag through clutter at object height. Intentional for side grasps
   in a clear corridor?

8. **Post-release retract targets the *last* approach hover** (`:609`) — correct for
   approach→pick→approach→release plans; a plan without the second approach retracts low
   and sideways across the table back to the pick hover. Should release require a
   preceding approach over the release position (validator rule)?

9. **Startup home + `/joint_states` share the default mutually-exclusive callback group**
   (`:133-138,170`) — during the ~8 s blocking startup, joint-state updates freeze and an
   early skill goal sees stale joints. Acceptable startup window?

10. **Camera distortion asymmetry** — `deproject_pixel_to_3d`
    (`camera_services_node.py:757-768`) treats VLM pixels as undistorted (pinhole only)
    while the ChArUco pose uses `camera_info.d` (`charuco_utils.py:120-126`). Is the
    Orbbec color stream ISP-rectified (d≈0)? If not, corner-region deprojections are
    biased and `cv2.undistortPoints` should run first.

11. **Depth registration is an unstated precondition** — depth is deprojected with the
    *color* intrinsics; correct only because `run_orbbec_registered.sh` sets
    `depth_registration:=true`. Worth a runtime `frame_id` check, or intentionally
    unguarded?

12. **Calibration averages translation over 5 samples but keeps only the last rotation**
    (`camera_services_node.py:444-447`). Rotation noise has a lever-arm effect (~0.5° at
    1 m ≈ 9 mm). Deliberate simplification?

13. **`local_plane_centroid` returns `top_z` = max survivor z, not the plane mean**
    (`:831-838`), so reported height rides the noisiest high pixel (up to `z_tol`=1 cm),
    and `Z_OFFSET_M` (+1 cm) stacks on top. Intentional "very top surface" bias?

14. **One bad pixel fails the whole Deproject batch** (`:298-302`) and hence the whole
    plan. Intentional all-or-nothing contract, or would per-point validity flags serve the
    planners better?

15. **`CharucoConfig.z_sign` default `-1.0`** (`charuco_utils.py:21`) contradicts
    `config.py:147` (`1.0`, "fixed from -1.0") and the stale launch comment
    (`camera_services.launch.py:62-64`). Visualization-only, but which sign is canonical?
    Align the dataclass default so a direct construction can't regress it.

16. **UR driver `ERROR_MARKERS` breadth** (`ur_driver_supervisor.py:60-66`) — bare
    substrings like `'Timeout'` match benign controller warnings and abort an attempt
    that might have succeeded. Are these markers tuned against real driver logs, or
    should they be anchored to the specific failure lines?

17. **Camera-service "starting…" semantics** (`app.js:588-590` + supervisor readiness) —
    `ready` means `/camera/get_image` is reachable, which requires
    `camera_services_node` from the *stack*, not the Orbbec script the supervisor owns.
    With the Orbbec driver up but the stack stopped, the card shows "starting…"
    indefinitely. Intended, or should readiness probe the Orbbec topics instead?

18. **CoT-SC replans on every `force_replan`** (`cot_sc.py:89`) while FHP only replans in
    `ffhp` mode (`fhp_ffhp.py:84-87`) and ReAct/AlwaysAct ignore it — is the differing
    `force_replan` semantics across methods intentional? (Latent today: the ROS planners
    build a fresh agent per request.)

19. **ReAct "reasoning" steps emit `wait(time=0.0)` actions** (`react.py:59`) which
    `run_plan_loop` records as real plan steps — the executed plan contains no-op waits,
    and in VLM mode every ReAct step re-sends the same frozen image with no execution
    feedback between steps. Accepted limitation of ReAct-in-a-planner, or should
    reasoning steps be filtered out of the returned plan?

20. **`reasoning_effort` is silently dropped for non-Groq providers**
    (`llm_client.py:65,89-90` and `vlm_client.py:107,152-153` — only the `_call_groq`
    branches forward it; `forced_json_schema` likewise). Config documents it as
    Groq-only, but the GUI offers it whenever mode is VLM/VLM_LLM regardless of the
    selected provider — surface a warning, or restrict the GUI field to Groq models?
